# ds-analytics

**Figma Design System Auditor** — плагин Figma, который сам находит проблемы в файле и сам приводит дизайнера к месту проблемы.

Две оси ценности:

1. **Поиск проблем** — аудит слоёв, компонентов, переменных, структуры, контента и a11y.
2. **Решение проблем** — навигация к ноде в один клик, массовые автофиксы с превью, undo одной транзакцией, ignore-лист.

Дифференциация против насыщенного рынка линтеров хардкода (Design Lint и аналоги):

- **Impact analysis** — что сломается, если удалить токен / переименовать компонент / схлопнуть варианты.
- **Adoption-тренд** — снапшоты состояния файла во времени. Разовый скан — инструмент, тренд — продукт.
- **Layer-aware правила токенов** — проверка соблюдения слоёв ДС, а не факта наличия переменной.

## Статус

**Pre-alpha. Правил ещё нет, но отчёт уже работает.** Плагин показывает, насколько файл живёт на дизайн-системе: доля компонентов из библиотеки, покрытие токенами, источники токенов, приоритеты «с чего начать», **impact-анализ токенов** («что сломается, если удалить»), переход к слою по клику, тренд по замерам во времени и экспорт отчёта в Markdown.

Это релиз 3 из паспорта, пришедший раньше срока — он не зависит от валидации сигнала. И он же несёт главную ценность: разовый скан это инструмент, тренд это продукт.

Готово ядро:

| Модуль                 | Что делает                                                  |
| ---------------------- | ----------------------------------------------------------- |
| `scanner/traversal.ts` | Обход с чанкингом, ленивой постраничной загрузкой и отменой |
| `scanner/cache.ts`     | Инкрементальная инвалидация по `nodechange`                 |
| `scanner/variables.ts` | Индекс переменных: `local` / `library` / `unavailable`      |
| `fixes/journal.ts`     | Собственный откат массового фикса                           |
| `storage/config.ts`    | Конфиг правил: устойчивый разбор, авторство, лимит          |
| `analysis/adoption.ts` | Отчёт adoption: откуда компоненты и токены                  |
| `analysis/usage.ts`    | Обратный индекс: токен → где используется                   |
| `analysis/snapshot.ts` | Снимки во времени и тренд по охвату                         |
| `storage/snapshots.ts` | История в документе: версия формата и ротация               |
| `shared/advice.ts`     | «С чего начать»: приоритеты, выведенные из отчёта           |
| `shared/export.ts`     | Отчёт в Markdown — то, что уносят из плагина                |
| `ui/parts/`            | Дизайн-система интерфейса и экраны отчёта                   |

Все четыре механизма паспорт декларировал без опоры в Figma API — расхождения найдены аудитом и закрыты решениями в [docs/decisions/](docs/decisions/).

Ближайший гейт — не написание кода, а **валидация сигнала правил на боевых файлах**: [протокол](docs/validation/protocol.md), [таблица результатов](docs/validation/results.md). При сигнале < 70% правило не идёт в продукт. Пока таблица не заполнена, правила в `src/main/rules/` не пишутся.

Инструмент для замера готов и ждёт боевых файлов — ветка [`spike/signal-probe`](https://github.com/egorovdnikita/ds-analytics/tree/spike/signal-probe). В `main` она не мержится: оттуда переносятся цифры, а не код.

## Разработка

```
npm ci
npm run verify     # то же, что гоняет CI: typecheck + lint + format + test + build
npm run build      # затем Plugins -> Development -> Import plugin from manifest
```

Границы из паспорта держат не договорённости, а раздельные `tsconfig` и ESLint: React в `src/main` не компилируется, `figma.*` в `src/ui` не линтуется, синхронные Figma-API запрещены правилом. Подробнее — [CONTRIBUTING.md](CONTRIBUTING.md).
