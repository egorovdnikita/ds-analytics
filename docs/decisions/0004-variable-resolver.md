# 0004. Библиотечные переменные — три состояния и двухфазный скан

**Статус:** принято, 2026-08-23
**Контекст:** [pre-launch аудит, блок B4](../pre-launch-audit.md)

## Проблема

Паспорт называет риск («библиотечные переменные не видны полностью без импорта»), но решения не даёт. Без решения правило `broken-alias` на любом файле-потребителе библиотеки выдаст сотни ложных срабатываний: биндинг на переменную, которую плагин не смог разрезолвить, выглядит как биндинг на удалённую.

Разница принципиальна:

- **переменная удалена** — это реальная проблема, о ней надо говорить;
- **переменная недоступна плагину** — это ограничение инструмента, и говорить о ней нельзя.

Отличить их постфактум невозможно, поэтому состояние должно быть в модели, а не выводиться на месте.

## Следствие, которого нет в паспорте: скан двухфазный

Паспорт требует двух вещей одновременно:

1. «Индекс переменных строится до обхода дерева».
2. «Правило **никогда** не делает `async` вызовов внутри `check`».

Но `getLocalVariablesAsync` отдаёт **только локальные** переменные. Библиотечная переменная, использованная в файле, достаётся лишь `getVariableByIdAsync(id)` — по одному id и асинхронно. Список нужных id известен только **после** обхода дерева, когда собраны все биндинги.

Значит порядок такой:

```
1. Индекс локальных переменных и коллекций   (async, до обхода)
2. Обход дерева, сбор bound variable ids     (async, чанкованный)
3. Гидрация неизвестных id                   (async, после обхода)
4. Прогон правил                             (полностью синхронный)
```

Формулировку паспорта «индекс переменных строится до обхода дерева» надо читать как «**локальный** индекс — до обхода; библиотечный достраивается после».

## Решение

**Три состояния, явно, в типе:**

- `local` — переменная найдена, `remote === false`;
- `library` — переменная найдена, `remote === true`;
- `unavailable` — `getVariableByIdAsync` вернул `null`.

Правила обязаны обрабатывать `unavailable`, и **дефолт — молчать**. Резолвер даёт для этого явный предикат `canJudge(id)`: правило, выносящее вердикт о переменной, спрашивает разрешение, а не проверяет `!== null` по своему усмотрению.

`resolve(id)` — **синхронный**: он читает уже построенный индекс и никогда не ходит в API. Это то, что позволяет `check` оставаться чистой функцией.

## Слои токенов

`layerOf(collectionName)` сопоставляет коллекцию слою по конфигу `tokenLayers`. Если конфига нет, `areLayersConfigured` возвращает `false`, и правило `tokens/layer-violation` **отключается, а не гадает** — прямое требование паспорта.

Сопоставление по имени коллекции регистронезависимое и по точному совпадению: подстрока дала бы `Semantic` внутри `Semantic Legacy`, что тихо неверно.

## Последствия

- Кэш `unavailable` держится по id: повторный `getVariableByIdAsync` на тот же мёртвый id за скан не делается.
- Гидрация устойчива к ошибкам отдельного id: упавший запрос трактуется как `unavailable`, а не роняет скан целиком.
- `orphan-variable` этим решением **не чинится** — см. блок B5 аудита. Резолвер видит один файл; переменная, не используемая здесь, может использоваться потребителями библиотеки.
