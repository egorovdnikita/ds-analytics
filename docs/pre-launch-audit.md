# Pre-launch аудит — ds-analytics

Дата: 2026-08-23 · Состояние репозитория на момент аудита: кода нет, только паспорт проекта.

---

## Вердикт

Паспорт проекта сильный: позиционирование отстроено от конкурентов, ограничения производительности осознаны, DoD для правила написан. Но **между паспортом и запуском лежат пять групп работ, три из которых — блокеры**, и ни одна не является «написать больше правил».

Главный риск проекта — **не производительность и не количество правил, а два обещания, которые дал паспорт, но которые Figma Plugin API не отдаёт даром**: атомарный undo массового фикса и инкрементальный ре-скан по хэшу ноды. Оба заявлены как решённые (`fixes/applier.ts` — «транзакции», `scanner/cache.ts` — «хэш по version-подобной сигнатуре»), но ни у того ни у другого нет прямой опоры в API. См. блок B — это надо закрыть проектным решением до первой строки `main/`.

Порядок работ: **A → B → C → E → D**. Блок A выполняется до кода и может отменить проект.

## Блок A. Валидация сигнала — гейт №0

Паспорт сам ставит этот гейт («если сигнал ниже 70% — продукт мёртв»), но не описывает процедуру. Без процедуры гейт не сработает: будет соблазн засчитать его «на глаз».

### A1. Зафиксировать методику замера

- [ ] Взять **3 боевых файла разного профиля**: зрелая ДС с библиотекой, продуктовый файл-потребитель библиотеки, файл-помойка без ДС. Один файл даст нерепрезентативную цифру.
- [ ] Прогнать вручную 5 правил-кандидатов. Обязательно включить **`components/detached-instance`** — это самое эвристичное правило в каталоге и вероятный источник провала по сигналу.
- [ ] Для каждого срабатывания зафиксировать вердикт живого дизайнера: `реальная проблема` / `ложное` / `намеренно так`. Третья категория — не ложное срабатывание, но и не проблема; она определяет объём работы по ignore-листу.
- [ ] Сигнал = `реальные / (реальные + ложные)`. Считать **по каждому правилу отдельно**, не средним по больнице: одно шумное правило утопит доверие ко всем остальным.

### A2. Отдельно провалидировать дифференциатор

`tokens/layer-violation` — правило, ради которого проект существует. Оно требует поля `tokenLayers` в конфиге.

- [ ] Проверить на боевых файлах, что **коллекции переменных вообще именуются так, что слои различимы**. Если в реальных ДС коллекции называются `Colors`, `Colors 2`, `New colors final` — правило неприменимо без ручной настройки на каждом файле, и его ценность как «фичи из коробки» падает до нуля.
- [ ] Если различимость низкая — заложить **мастер настройки слоёв при первом запуске** (показать список коллекций, попросить разметить). Это меняет объём MVP и должно быть решено сейчас, а не после релиза.

### A3. Критерий выхода из блока

Ни строчки кода правил, пока нет таблицы «правило → сигнал → вердикт (берём / в `info` / выкидываем)» по 3 файлам.

## Блок B. Архитектурные дыры — закрыть до кода ⚠️ БЛОКЕР

Это находки аудита: места, где паспорт декларирует результат, но не декларирует механизм, а механизм неочевиден.

### B1. Атомарный undo массового фикса ⚠️

**Обещание паспорта:** «Все изменения одного bulk-действия — одна отменяемая транзакция».

**Проблема:** в Figma Plugin API нет транзакционного API — нет `beginTransaction` / `commit`. Группировка правок в один шаг истории — побочный эффект того, как Figma батчит изменения плагина, а **чанкинг обхода через `await setTimeout(0)` (который паспорт требует в блоке производительности) с высокой вероятностью разрывает батч на несколько шагов undo**. Два требования паспорта конфликтуют напрямую.

Пользователь, который применил 200 фиксов и нажал Cmd+Z, получит откат 12 фиксов. Это ровно тот сценарий, про который паспорт пишет «хоронит доверие навсегда».

**Что сделать:**
- [ ] Проверить эмпирически на текущей версии API: применить N правок с yield и без, посчитать шаги истории.
- [ ] Если батч рвётся — выбрать стратегию и записать её в паспорт:
  - **(а)** применять фиксы синхронно без yield, ограничив размер батча тем, что успевает пройти без фриза (например 500 правок), и честно показывать в UI «будет применено 500 из 2000, продолжить?»;
  - **(б)** реализовать **собственный откат**: перед фиксом сохранять предыдущее значение свойства, отдавать кнопку «Отменить последнее массовое действие» в UI плагина, не полагаясь на Cmd+Z;
  - **(в)** комбинация: свой откат как гарантия + попытка уложиться в один нативный шаг.
- [ ] Вариант (б) — самый честный и требует поля `previousValue` в `FixAction`. Это влияет на `shared/types.ts`, то есть на контракт. Решать сейчас.

### B2. Хэш ноды для инкрементального ре-скана ⚠️

**Обещание паспорта:** `cache.ts` — «хэш ноды (`id + version-подобная сигнатура`)».

**Проблема:** у `SceneNode` нет публичного поля версии или времени модификации. «Version-подобная сигнатура» — это либо сериализация всех проверяемых свойств ноды (что стоит примерно столько же, сколько сам прогон правил, и обнуляет выигрыш), либо самообман.

**Что сделать:**
- [ ] Отказаться от иллюзии дешёвого хэша. Реальные варианты:
  - **(а)** инвалидация по событию `figma.on('documentchange')` — подписка даёт список изменённых нод; пересчитывать только их и их предков. Это рабочий механизм, и он **не хэш**; переписать `cache.ts` в паспорте под него.
  - **(б)** хэш только по узкому набору полей, релевантных зарегистрированным правилам (правило объявляет, какие свойства читает — расширить тип `Rule` полем `reads: NodeProperty[]`).
- [ ] Вариант (а) предпочтителен и дешевле. Но `documentchange` не переживает перезапуск плагина — значит кэш живёт только внутри сессии, и «инкрементальный ре-скан» в паспорте надо ограничить до «внутри сессии». Это снижение обещания — зафиксировать явно.

### B3. Динамическая загрузка страниц и full-file скан ⚠️

**Проблема:** современный манифест плагина требует поля `documentAccess`. В режиме `"dynamic-page"` страницы документа не загружены по умолчанию, и обход всего файла требует явной асинхронной загрузки страниц; синхронные обходы и синхронный `getNodeById` в этом режиме недоступны.

Паспорт этого не учитывает: `indexer.ts` описан как «один `findAll()` → NodeIndex», что для full-file скана в dynamic-page режиме неверно.

**Что сделать:**
- [ ] Свериться с актуальной докой Figma по `documentAccess` и требованиям к новым плагинам на момент старта разработки — режим и его ограничения могли измениться.
- [ ] Заложить в `traversal.ts` **асинхронную постраничную загрузку** с прогрессом по страницам, а не только чанкинг по нодам. Full-file скан на 40-страничном файле — это два уровня прогресса, а не один.
- [ ] Все обращения к нодам по id (навигация из списка issue, ignore-лист) — через async-вариант. Синхронный `getNodeById` в коде запретить линтером.
- [ ] Проверить, что дефолтный скоуп «страница» действительно избавляет от загрузки остальных страниц — если да, это ещё один аргумент за такой дефолт, и его надо записать в паспорт как архитектурное обоснование, а не как UX-предпочтение.

### B4. Библиотечные переменные

Паспорт риск называет, но решения не даёт («заложить в архитектуру сразу»).

**Что сделать:**
- [ ] Ввести **`VariableResolver`** — единственную точку доступа к переменным для всех правил, с явной моделью трёх состояний: `локальная` / `библиотечная, импортированная` / `библиотечная, недоступна`.
- [ ] Правила обязаны обрабатывать третье состояние. Дефолт — **молчать, а не ругаться**: биндинг на переменную, которую плагин не смог разрезолвить, не является `broken-alias`. Без этого на любом файле-потребителе библиотеки правило `broken-alias` выдаст сотни ложных срабатываний и убьёт сигнал.
- [ ] Покрыть тестами именно третье состояние — оно самое вероятное на боевых файлах и самое забываемое в разработке.

### B5. `orphan-variable` даёт ложные срабатывания by design

**Проблема:** переменная, не используемая в текущем файле, может активно использоваться в файлах-потребителях библиотеки. Плагин видит один файл. Пометить такую переменную как сироту — прямая дезинформация, ведущая к удалению живого токена.

**Что сделать:**
- [ ] Ограничить правило файлами, не являющимися источником библиотеки, либо
- [ ] Понизить до `info` с формулировкой, которая честно говорит об ограничении области видимости («не используется **в этом файле**; проверьте потребителей библиотеки вручную»), и
- [ ] **Не давать `fix`** этому правилу ни при каком раскладе.

### B6. `a11y/token-pair-contrast` — комбинаторика

Проверка «пар токенов» без ограничения — это N×M пар, из которых осмысленны единицы. Отчёт на 4000 пар бесполезен.

**Что сделать:**
- [ ] Определить источник пар: реально встречающиеся в файле сочетания `fill` ноды + `fill` её текстового потомка, а не декартово произведение коллекции.
- [ ] Учесть режимы (light/dark): пара валидна во всех режимах или ни в одном. Пересечение с правилом `missing-mode-value`.

### B7. Рост снапшотов против лимита plugin data

Релиз 3 пишет снапшоты в `documentPluginData`. Хранилище plugin data ограничено по объёму (паспорт называет ~100 KB на запись для нод). Тренд, копящийся неделями, упрётся в лимит и начнёт молча терять данные.

**Что сделать:**
- [ ] Заложить политику ротации сразу при проектировании формата снапшота: N последних + агрегаты, а не полная история.
- [ ] Формат снапшота — версионированный (`{ v: 1, ... }`), иначе миграция тренда при изменении набора метрик потеряет историю.

### B8. Конфиг в документе — конфликт одновременных правок

`figma.root.setPluginData('audit-config')` при командной работе — last-write-wins без уведомления. Два DS-мейнтейнера переписывают конфиг друг друга молча.

**Что сделать:**
- [ ] Добавить в конфиг `updatedBy` + `updatedAt`, показывать в настройках «изменён X, дата». Полноценный мердж не нужен, нужна видимость.

## Блок C. Инфраструктура репозитория

Ничего из этого не существует. Каждый пункт — предпосылка соглашений, которые паспорт уже объявил обязательными.

### C1. Каркас сборки
- [ ] `package.json`, `tsconfig.json` c `strict: true`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`
- [ ] `@figma/plugin-typings` в devDependencies
- [ ] `manifest.json` с обязательными полями: `editorType`, `documentAccess`, `networkAccess` (для MVP — без сети; поле обязательно даже при её отсутствии)

### C2. Качество кода — то, что делает соглашения паспорта исполнимыми
- [ ] ESLint + `@typescript-eslint` с `no-explicit-any: error` — паспорт запрещает `any`, линтер это обеспечивает
- [ ] **Правило границ импортов** (`eslint-plugin-boundaries` или `no-restricted-imports`): React не импортируется в `src/main/**`, `figma.*` не используется в `src/ui/**`. Паспорт объявил это соглашением — без линтера оно продержится до первого дедлайна
- [ ] Запрет синхронных API-вызовов, несовместимых с dynamic-page (см. B3), через `no-restricted-syntax`
- [ ] Prettier + lint-staged + pre-commit hook

### C3. Тесты
- [ ] Vitest + **фабрика моков нод** (`test/factories/node.ts`). Это ключевой файл: DoD требует по 3 теста на правило, и без удобной фабрики написание тестов станет дороже написания правил, после чего DoD перестанут соблюдать
- [ ] Порог покрытия для `src/main/rules/**` в конфиге Vitest
- [ ] Тест-хелпер проверки **идемпотентности фикса** (применить дважды → второй раз ноль изменений) — DoD этого требует, значит нужен готовый хелпер, а не ручная проверка

### C4. CI
- [ ] GitHub Actions: `typecheck` + `lint` + `test` + `build` + `size-check` на PR
- [ ] Branch protection на `main`: запрет прямого пуша, обязательные проверки
- [ ] ⚠️ **Текущий токен `gh` не имеет scope `workflow`** — файлы в `.github/workflows/` не запушатся. Перед добавлением CI выполнить:
  ```
  gh auth refresh -h github.com -s workflow
  ```

### C5. Процесс
- [ ] PR-шаблон с чек-листом Definition of Done для правила — DoD из паспорта, скопированный в шаблон, соблюдается; DoD в отдельном файле — нет
- [ ] `CONTRIBUTING.md` с рецептом «как добавить правило» (один файл + регистрация + 3 теста)

## Блок D. Публикация в Figma Community ⚠️ БЛОКЕР релиза

Не техническая работа, но срывает дату, если начать за неделю до релиза. Требования проверить по актуальной доке Figma перед подачей — они меняются.

- [ ] **Лицензия репозитория.** Сейчас её нет — это блокер и для публикации, и для внешней контрибуции. Выбор зависит от модели монетизации: MIT для полностью открытого, проприетарная — если планируется платный тариф на Impact analysis / Adoption

- [ ] Аккаунт паблишера, обложка, иконка, описание, скриншоты, теги
- [ ] Заложить **буфер на ревью Figma** — сроки не контролируются командой
- [ ] Канал поддержки и адрес для баг-репортов
- [ ] Политика версионирования и changelog

## Блок E. Продуктовые решения, влияющие на код

- [ ] **Формулировки сообщений.** DoD требует «что не так и почему». Написать текст **до** реализации правила: правило, для которого не формулируется внятное «почему», — кандидат на выброс. Это дешёвый фильтр каталога
- [ ] **Пресеты.** Паспорт упоминает разные пресеты для DS-мейнтейнера и продуктового дизайнера, но `extends` в схеме конфига поддерживает только `"recommended"`. Определить набор пресетов и семантику `extends` до фиксации формата конфига — иначе миграция версии 1 → 2
- [ ] **Поведение при отсутствующем `tokenLayers`.** Паспорт: правило отключается, а не гадает. Нужен видимый UI-сигнал «правило отключено, потому что не настроено» — иначе пользователь считает, что нарушений нет
- [ ] **Пустое состояние.** Первый запуск на чистом файле не должен выглядеть как «плагин не работает»
- [ ] **Формат экспорта отчёта** (релиз 3) — определяет, нужен ли `networkAccess` вообще
