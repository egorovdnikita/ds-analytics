# Результаты валидации сигнала

Заполняется по [протоколу](protocol.md). Замеры делает [пробник](https://github.com/egorovdnikita/ds-analytics/tree/spike/signal-probe), вердикты — дизайнер.

**Статус: три замера на двух профилях, судейство не начиналось. Правила не пишутся.**

Главный открытый вопрос — применимость `tokens/layer-violation`, главного дифференциатора проекта. Ответ пока **не получен**: вывод, сделанный после прогона по одной странице, оказался неверным на полном файле. См. блок про слои.

**Методическая заметка.** Каждый из трёх прогонов исправлял не файл, а измерительный инструмент: сначала `raw-fill` считал стили хардкодом, потом `detached-instance` не видел библиотечных мастеров, потом ноль у `layer-violation` оказался неотличим от неприменимости. Ни одну цифру нельзя брать без ответа на вопрос «а могло ли правило вообще сработать».

### Что прогон уже доказал, до всякого судейства

1. **`raw-fill` без учёта paint-стилей и инстансов непригоден.** Разница между 5798 и 38 — это разница между продуктом и генератором шума.

## Что дало сравнение двух профилей

| Правило                        | Потребитель (25804 нод) | Зрелая ДС (5236 нод) | Читается как                                                     |
| ------------------------------ | ----------------------- | -------------------- | ---------------------------------------------------------------- |
| `tokens/raw-fill`              | 38                      | **2**                | Здоровое поведение: много на грязном файле, почти ноль на чистом |
| `structure/default-name`       | 388                     | **1**                | То же                                                            |
| `components/detached-instance` | 9                       | **183**              | **Инверсия — подпись сломанной эвристики**                       |
| `tokens/broken-alias`          | 0                       | 0                    | Не срабатывает нигде — судить нечего                             |
| `tokens/layer-violation`       | 0                       | 0                    | Проверять нечего ни там, ни там                                  |

### `raw-fill` и `default-name` ведут себя правильно

Это первая содержательная проверка из протокола, шаг 1: «не шумит ли плагин там, где всё хорошо». Оба правила её прошли. На зрелой ДС они почти молчат, на продуктовом файле находят десятки и сотни. Именно такая форма и нужна.

### `detached-instance` сломан

183 срабатывания на **более чистом** файле против 9 на грязном. Причина найдена: под совпадение по имени попадали фреймы внутри определений компонентов — внутренности мастера, а не оторванные инстансы. Исправлено, требуется пересчёт.

**Но цифру после пересчёта тоже нельзя переносить на правило из паспорта.** Пробник сравнивает **имена**, а паспорт требует «эвристику по структурному совпадению с мастером». Это принципиально разные проверки, и вторая ещё не измерена.

### `broken-alias` не удалось провалидировать

Ноль срабатываний на обоих файлах при 10839 биндингах суммарно. Это **не хороший сигнал и не плохой — это отсутствие данных**. Правило, которое ни разу не сработало на двух боевых файлах, нельзя ни взять, ни выбросить по протоколу: судить нечего.

Практический вывод: сломанные алиасы в Figma, похоже, редки. Правило — кандидат в `info` или за пределы MVP, но по причине «нечего ловить», а не «плохой сигнал».

### Поправка к выводу прогона 2

Прогон 2 шёл по **одной странице** и показал 8 коллекций. Полный файл показывает около двадцати:

```
★ Brand Colors · ◐ Mode ×5 · ⛶ Radius · Ω Spacing · # Size · T Typography ×3
][ Grid ×3 · ]|[ Grid · ✦ Opacity ×2 · Collection 1 ×3 · Primitives · ⛶ Corner
Theme colors · Colors ×3 · Kit ×2 · System
```

**Среди них есть коллекция `Primitives`.** Значит вывод прогона 2 — «слоистой архитектуры нет вообще» — сделан по неполным данным и неверен. Слой примитивов в этой системе существует, он просто не попал в ту страницу, по которой я судил.

Урок методический: **скоуп «страница» не годится для выводов о структуре файла.** Считать сигнал по странице можно, судить об архитектуре токенов — нет.

### `raw-fill`: 2 на странице против 20 622 на файле

Разница в четыре порядка. Одна страница ДС почти идеально токенизирована, файл целиком — нет. Скорее всего остальные страницы это черновики, песочницы и документация, а не продакшен.

**Прямое следствие для продукта:** full-file скан по файлу дизайн-системы даёт отчёт, в котором тонет полезное. Либо нужен способ исключать непродакшен-страницы, либо дефолтный скоуп «страница» из паспорта — не удобство, а необходимость.

## Применим ли `layer-violation` из коробки — ПОКА НЕ ЗНАЕМ

Правило требует разметки `tokenLayers`: какие коллекции считать примитивами, какие семантикой, какие компонентными. Вопрос шага A2 протокола: читаются ли слои по именам коллекций.

| Файл        | Скоуп         | Имена коллекций                                                            | Слои различимы? |
| ----------- | ------------- | -------------------------------------------------------------------------- | --------------- |
| Потребитель | страница      | `◐ Mode` · `][ Grid` · `T Typography` · `Collection 1` ×3 · `Theme colors` | Нет             |
| Зрелая ДС   | страница      | 8 коллекций, все по типу свойства                                          | Нет             |
| Зрелая ДС   | **весь файл** | ~20 коллекций, **включая `Primitives`**                                    | **Частично**    |

### Картина сложнее, чем казалось после двух прогонов

Основная масса коллекций разложена **по типу свойства**: цвета, режим, радиусы, отступы, размеры, типографика, сетка, прозрачность. Эта структура ортогональна слоям.

Но в файле **есть коллекция `Primitives`**, а также `System`, `Kit`, `Theme colors`. Слой примитивов в системе выделен — просто не он организует всю библиотеку токенов.

При этом ландшафт разросшийся: около двадцати коллекций, из них `Collection 1` ×3, `Colors` ×3, `Mode` ×5, и одновременно `][ Grid` и `]|[ Grid`. Это отдельная находка про состояние системы. Для нашего вопроса важно другое: **разметка `tokenLayers` здесь возможна, но потребует ручного решения по каждой из двадцати коллекций.**

### Следствия для продукта

Это не проблема настройки. Это проверка гипотезы, на которой стоит главный дифференциатор проекта, и на данной системе гипотеза **не подтвердилась**.

### Что нужно, чтобы закрыть вопрос

Прогон 3 показал `layer-violation` = 0 и подписал это как «чисто». Верить нельзя: ноль нарушений при нуле переменных в слое примитивов означает не здоровую систему, а то, что нарушать было нечего.

Пробник доработан. Теперь он показывает, **сколько переменных легло в каждый слой** и **сколько нод внутри определений компонентов**, и признаёт правило неприменимым, если проверять было нечего. Следующий прогон по всему файлу ДС ответит по-настоящему:

- примитивных переменных десятки, нод в мастерах тысячи, нарушений ноль → **система действительно чистая**, правило работает и на этом файле проблем не находит;
- примитивных переменных ноль → **`Primitives` не лёг** на наше сопоставление, и разметка потребует ручной работы.

Если подтвердится второе:

1. **Проверить шире.** Одна дизайн-система — не рынок. Нужны имена коллекций ещё из 3–5 чужих ДС; пробник их печатает, это дёшево.
2. **Мастер разметки слоёв в MVP.** Показать коллекции, попросить разметить. Объём, которого в roadmap не было.
3. **Убрать из MVP.** Тогда MVP — ещё один линтер хардкода, ровно то, от чего проект отстраивался.

Решение продуктовое, не техническое.
